Automating & Managing Power Workloads on IBM Power Virtual Server

Open the Fedora terminal on the lab machine (Windows Subsystem for Linux). Build an AIX 7.3 server on IBM Power Virtual Server, either by typing every ibmcloud command or by letting Terraform do the heavy lifting. Each track has its own architecture diagram that fills in as you go. Finish one, then try the other.

Choose your track

Both take about 90 minutes and end with you logged in to AIX. You can switch at any time; your progress on each track is kept.

CLI only

You type every ibmcloud command yourself. You build an AIX server in PowerVS, starting it first because it takes longest, then an Ubuntu server in a VPC while it builds, join them with a Transit Gateway, and reach AIX two ways.

    Set up Fedora

    On the lab machine, open the Fedora terminal in Windows Subsystem for Linux. Install commands use sudo. You sign in to the lab account from that terminal in step 1.7.

    Install the tools

    1.1

    The lab machines run Fedora in the Windows Subsystem for Linux. Open that terminal. Package installs need sudo. This adds HashiCorp's repository, then installs Terraform, Ansible (the ansible-core package), and git, jq, and curl. If dnf asks to import the HashiCorp GPG key, answer yes.

    you@fedora:~
    curl -fsSL https://rpm.releases.hashicorp.com/fedora/hashicorp.repo | sudo tee /etc/yum.repos.d/hashicorp.repo
sudo dnf install -y terraform ansible-core git jq curl
    1.2

    Fedora does not ship the IBM Cloud CLI. IBM's installer copies ibmcloud to /usr/local/bin. sudo runs that installer as an administrator.

    you@fedora:~
    curl -fsSL https://clis.cloud.ibm.com/install/linux | sudo sh

    Install the plugins

    1.3

    The base ibmcloud CLI talks to each service through a plugin. This one adds ibmcloud pi, the commands for Power Virtual Server. Run it as yourself, without sudo. Plugins are stored in your home directory, and a sudo install would hide them from your later commands. -f skips the "are you sure" prompt.

    you@fedora:~
    ibmcloud plugin install power-iaas -f
    1.4

    Adds ibmcloud is, the commands for VPC. The plugin package is vpc-infrastructure. Run it as yourself, the same way as power-iaas.

    you@fedora:~
    ibmcloud plugin install vpc-infrastructure -f
    1.5

    Adds ibmcloud tg, the commands for Transit Gateway. The plugin is called tg-cli but the command is tg. Run it as yourself.

    you@fedora:~
    ibmcloud plugin install tg-cli -f
    1.6

    Runs each plugin's help quietly to prove it works. You want three OK lines.

    you@fedora:~
    for c in pi is tg; do
  ibmcloud $c help >/dev/null 2>&1 \
    && echo "ibmcloud $c OK" || echo "ibmcloud $c MISSING"
done

    Pick the region and resource group

    1.7

    The Fedora terminal starts signed out. --sso prints a link and a one-time code. Open the link in the Windows browser, enter the code, and choose the lab account.

    you@fedora:~
    ibmcloud login --sso -r us-south
    1.8

    Sets the region for everything after this. us-south is Dallas, which also holds the dal10 PowerVS datacenter.

    you@fedora:~
    ibmcloud target -r us-south
    1.9

    Lists the resource groups in the account. A resource group is a folder for access and billing; everything you create goes in one. Note the Name. TechZone accounts usually have a single group with a generated name like eid-6add89fa....

    you@fedora:~
    ibmcloud resource groups
    1.10

    Saves the group name in a shell variable so later commands can reuse it as $RG_NAME. Replace <group-name> with the name from the list.

    you@fedora:~
    export RG_NAME="<group-name>"
    1.11

    Makes that group the default, so everything you create from now on lands in it.

    you@fedora:~
    ibmcloud target -g "$RG_NAME"
    1.12

    The PowerVS command in step 2 wants the group's ID, not its name. --id prints only the ID, and $( ) captures it into $RG_ID.

    you@fedora:~
    export RG_ID=$(ibmcloud resource group "$RG_NAME" --id)

    Set your prefix

    1.13

    Your attendee number, 1 to 30. Replace <your-number> with it.

    you@fedora:~
    export SEAT=<your-number>
    1.14

    Turns your number into your prefix: printf pads it to two digits, so 7 becomes pvs-07. Every resource you create starts with $P, so yours never collide with your neighbour's.

    you@fedora:~
    export P=$(printf 'pvs-%02d' "$SEAT")
    1.15

    Prints both values. Neither should be empty.

    you@fedora:~
    echo "prefix=$P  group=$RG_ID"

    Make your SSH key

    1.16

    Makes sure your .ssh folder exists and only you can read it. SSH refuses keys kept in folders others can open.

    you@fedora:~
    mkdir -p -m 700 ~/.ssh
    1.17Builds: SSH key pair

    Creates the one key pair you use for both servers. -t rsa -b 4096 is a 4096-bit RSA key, which PowerVS, AIX, and VPC all accept. -f names the files (pvs-lab and pvs-lab.pub), -N "" means no passphrase, and -C labels it with your prefix. The public half goes to IBM Cloud; the private half never leaves Cloud Shell.

    you@fedora:~
    ssh-keygen -t rsa -b 4096 -f ~/.ssh/pvs-lab -N "" -C "$P"
    1.18

    Tells SSH two things for every connection: use your lab key, and trust a server's host key the first time without asking. You still name the user each time: root on AIX, ubuntu on the VSI. The config also applies when you hop through one server to reach another in step 5.

    you@fedora:~
    cat >> ~/.ssh/config <<EOF
Host *
  IdentityFile ~/.ssh/pvs-lab
  StrictHostKeyChecking accept-new
EOF
    1.19

    SSH ignores a config file that other users could change, so make it yours only.

    you@fedora:~
    chmod 600 ~/.ssh/config

https://raw.githubusercontent.com/emaadparacha/ibm-techxchange-2026/main/pvs-wait.py
    1.21

    Shows what it can watch. You will use it four times in this lab.

    python3 pvs-wait.py --help

    Save your variables

    Writes your variables to a file. In a new terminal, run source ~/pvs-lab.env to get them all back. pvs-wait.py reads this file too.

    you@fedora:~

EOF

    Build PowerVS and start the AIX server

    The AIX server takes 15 to 20 minutes to build, so you start it as early as possible and build the VPC side in step 3 while it runs.

    Create the workspace

    2.1Builds: PowerVS workspace

    A workspace is the PowerVS container that holds your servers, images, subnets, and keys. dal10 is a Dallas datacenter with a Power Edge Router, which lets a workspace plug straight into a Transit Gateway. --plan public is the standard IBM-hosted offering. The command returns right away while the workspace keeps provisioning in the background.

    you@fedora:~
    ibmcloud pi workspace create "$P-ws" \
  --datacenter dal10 --group "$RG_ID" --plan public
    2.2Wait game

    The workspace takes 5 to 15 minutes. This checks its state every 15 seconds (with ibmcloud resource service-instance "$P-ws") and returns once it is active. While it waits, pvs-wait.py offers three games: Power Trivia, Subnet Sprint, and Packet Snake. The game stops the moment the resource is ready. Not in the mood? Add --quiet to just watch the status.

    you@fedora:~
    python3 pvs-wait.py workspace
    2.3

    Every IBM Cloud resource has a CRN (Cloud Resource Name), a globally unique ID. --output json prints the workspace as JSON and jq -r pulls out that one field.

    you@fedora:~
    export WS_CRN=$(ibmcloud resource service-instance "$P-ws" --output json \
  | jq -r '.[0].crn')
    2.4

    Tells the CLI which workspace you mean. Every ibmcloud pi command after this acts on this workspace.

    you@fedora:~
    ibmcloud pi workspace target "$WS_CRN"

    Import your key and create two subnets

    2.5Builds: PowerVS SSH key

    Uploads your public key to PowerVS. When the server is created, PowerVS copies it into root's authorized_keys, which is how your private key gets you in.

    you@fedora:~
    ibmcloud pi ssh-key create "$P-key" --key "$(cat ~/.ssh/pvs-lab.pub)"
    2.6Builds: Private subnet

    The private subnet: addresses in 192.168.50.0/24 that only reach other IBM Cloud networks. The Transit Gateway will advertise it to your VPC in step 3. Its gateway is 192.168.50.1, which matters in step 4.

    you@fedora:~
    ibmcloud pi subnet create "$P-priv" --net-type private \
  --cidr-block 192.168.50.0/24 --dns-servers 9.9.9.9
    2.7Builds: Public subnet

    The public subnet: gives the server an internet address. Cloud Shell runs on the internet, not inside your VPC, so this is how it reaches AIX directly. PowerVS picks the address range itself.

    you@fedora:~
    ibmcloud pi subnet create "$P-pub" --net-type public
    2.8

    Shows both subnets with their IDs.

    you@fedora:~
    ibmcloud pi subnet list
    2.9

    Saves the private subnet's ID as $PRIV_ID. The jq filter searches the JSON for the object with your subnet's name.

    you@fedora:~
    export PRIV_ID=$(ibmcloud pi subnet list --json \
  | jq -r --arg n "$P-priv" \
      '.. | objects | select(.name? == $n) | (.networkID // .id)' \
  | head -1)
    2.10

    Saves the public subnet's ID as $PUB_ID.

    you@fedora:~
    export PUB_ID=$(ibmcloud pi subnet list --json \
  | jq -r --arg n "$P-pub" \
      '.. | objects | select(.name? == $n) | (.networkID // .id)' \
  | head -1)

    Copy an AIX image into your workspace

    2.11

    Lists IBM's stock images and keeps the AIX 7.3 ones. Their names start with 7300: 7300-03-00 is 7.3 Technology Level 3.

    you@fedora:~
    ibmcloud pi image list-catalog | grep 7300
    2.12

    Picks the newest AIX 7.3 level: keep names starting 7300-, sort them, take the last, and save its ID.

    you@fedora:~
    export STOCK_ID=$(ibmcloud pi image list-catalog --json \
  | jq -r '[.images[] | select(.name | startswith("7300-"))]
           | sort_by(.name) | last | .imageID')
    2.13Builds: AIX image copy

    Copies that stock image into your workspace, because servers boot from images inside the workspace. Stock image names cannot be changed, so the copy keeps its name.

    you@fedora:~
    ibmcloud pi image create "$STOCK_ID"
    2.14Wait game

    Waits for the copy to be active, usually a few minutes. A good moment for a quick round of Subnet Sprint.

    you@fedora:~
    python3 pvs-wait.py image
    2.15

    Saves the ID of the copy in your workspace. This is the ID the server needs, not the stock one.

    you@fedora:~
    export IMG_ID=$(ibmcloud pi image list --json | jq -r '.images[0].imageID')

    Start the AIX server

    2.16Builds: AIX server

    Starts building the AIX virtual server, which PowerVS calls an instance (on Power hardware it is an LPAR, a logical partition). The command returns as soon as the build starts. Do not wait for it: go straight on to step 3.

    you@fedora:~
    ibmcloud pi instance create "$P-aix" \
  --image "$IMG_ID" \
  --sys-type s1022 \
  --processor-type shared --processors 0.25 \
  --memory 4 \
  --storage-tier tier3 \
  --key-name "$P-key" \
  --subnets "$PUB_ID" --subnets "$PRIV_ID"
    --sys-type s1022
    A Power10 scale-out server model.
    --processor-type shared
    Borrow cores from a shared pool, the cheapest option.
    --processors 0.25
    A quarter of a core, plenty for a lab.
    --memory 4
    4 GB of RAM.
    --storage-tier tier3
    Boot disk at 3 IOPS per GB, the cheapest tier fine for a boot disk.
    --key-name
    Your PowerVS key, added for root.
    --subnets (twice)
    One network card on each subnet. The public one is listed first so it is the primary card and carries the default route.
    2.17

    Saves the server's ID. PowerVS usually calls the name field serverName and the ID pvmInstanceID; the filter also accepts name and id.

    you@fedora:~
    export AIX_ID=$(ibmcloud pi instance list --json \
  | jq -r --arg n "$P-aix" \
      '.. | objects | select(.serverName? == $n or .name? == $n)
         | (.pvmInstanceID // .id)' \
  | head -1)
    2.18

    Must not be empty. If it is, run ibmcloud pi instance list, copy the ID of $P-aix, and run export AIX_ID=<that ID> before saving.

    you@fedora:~
    echo "AIX_ID=$AIX_ID"
    2.19

    Adds this step's IDs to your file. >> appends instead of overwriting.

    you@fedora:~
    cat >> ~/pvs-lab.env <<EOF
export WS_CRN="$WS_CRN" PRIV_ID="$PRIV_ID" PUB_ID="$PUB_ID"
export IMG_ID="$IMG_ID" AIX_ID="$AIX_ID"
EOF
    ExpectYour key, two subnets, an active image, and a server that is building. In the diagram, the whole PowerVS workspace is filled in.

    While AIX builds: VPC, Ubuntu VSI, and Transit Gateway

    AIX is building in the background. Use the time to build the other side: a VPC with an Ubuntu server (VSI) in it, and a Transit Gateway joining the VPC to your PowerVS workspace.

    Create the VPC

    3.1Builds: VPC

    Creates your VPC (Virtual Private Cloud), a private network in IBM Cloud. IBM gives it an address range in each zone automatically, plus a default security group, network ACL, and routing table, which you can see in the output.

    you@fedora:~
    ibmcloud is vpc-create "$P-vpc"
    3.2Builds: VPC subnet

    Carves a subnet of 256 addresses out of the VPC's range in zone us-south-1. Your Ubuntu server will live here.

    you@fedora:~
    ibmcloud is subnet-create "$P-vpc-sn" "$P-vpc" \
  --zone us-south-1 --ipv4-address-count 256
    3.3

    Lists the VPC's address ranges, all 10.240.x.x. The Transit Gateway refuses to join networks whose ranges overlap, so confirm none of these is 192.168.50.x.

    you@fedora:~
    ibmcloud is vpc-address-prefixes "$P-vpc"
    3.4

    Saves the VPC's CRN. The Transit Gateway attaches networks by CRN.

    you@fedora:~
    export VPC_CRN=$(ibmcloud is vpc "$P-vpc" --output json | jq -r '.crn')

    Let SSH into the VPC

    3.5Builds: VPC SSH key

    VPC keeps its own list of SSH keys, separate from PowerVS, so upload the same public key here. The @ means "read the key from this file".

    you@fedora:~
    ibmcloud is key-create "$P-vpckey" @$HOME/.ssh/pvs-lab.pub
    3.6

    Every VPC gets a default security group, a firewall around each server. This saves its ID.

    you@fedora:~
    export SG_ID=$(ibmcloud is vpc "$P-vpc" --output json \
  | jq -r '.default_security_group.id')
    3.7Builds: SSH rule

    The default group only lets in traffic from its own members. This rule lets in SSH (TCP port 22) from anywhere, so Cloud Shell can reach your VSI. Replies to connections the VSI makes are always allowed back in.

    you@fedora:~
    ibmcloud is security-group-rule-add "$SG_ID" inbound tcp \
  --port-min 22 --port-max 22 --remote 0.0.0.0/0
    3.8

    Lets in ping (ICMP) from your PowerVS private subnet, so AIX can ping the VSI back in step 5. Only that one range is allowed, not the whole internet.

    you@fedora:~
    ibmcloud is security-group-rule-add "$SG_ID" inbound icmp --remote 192.168.50.0/24

    Create the Ubuntu VSI

    3.9

    Finds IBM's current Ubuntu 24.04 image among the public ones and saves its ID.

    you@fedora:~
    export VSI_IMAGE=$(ibmcloud is images --visibility public --output json \
  | jq -r '[.[] | select(.status == "available")
               | select(.operating_system.name == "ubuntu-24-04-amd64")][0].id')
    3.10Builds: Ubuntu VSI

    Creates a VSI (virtual server instance) in your VPC subnet. The positional arguments are: name, VPC, zone, profile, subnet. cx2-2x4 is a compute profile with 2 vCPUs and 4 GB of RAM. --keys puts your key on it.

    you@fedora:~
    ibmcloud is instance-create "$P-vsi" "$P-vpc" us-south-1 cx2-2x4 "$P-vpc-sn" \
  --image "$VSI_IMAGE" --keys "$P-vpckey"
    3.11Wait game

    A VSI boots in about a minute. This returns once it is running.

    you@fedora:~
    python3 pvs-wait.py vsi
    3.12

    New VSIs connect to their subnet through a network attachment, which points to a virtual network interface (VNI): the VSI's virtual network card, which holds its IP address. This saves the VNI's ID, because the floating IP attaches to the VNI.

    you@fedora:~
    export VNI_ID=$(ibmcloud is instance "$P-vsi" --output json \
  | jq -r '.primary_network_attachment.virtual_network_interface.id')
    3.13

    Saves the VSI's private address, a 10.240.0.x address in your subnet. AIX will ping it in step 5.

    you@fedora:~
    export VSI_PRIV=$(ibmcloud is instance "$P-vsi" --output json \
  | jq -r '.primary_network_attachment.primary_ip.address')
    3.14Builds: Floating IP

    A floating IP is a public internet address mapped to the VSI's private one. It is how Cloud Shell reaches the VSI. --vni binds it to the VSI's virtual network interface.

    you@fedora:~
    ibmcloud is floating-ip-reserve "$P-fip" --vni "$VNI_ID"
    3.15

    Saves the floating IP.

    you@fedora:~
    export VSI_IP=$(ibmcloud is floating-ip "$P-fip" --output json | jq -r '.address')
    3.16

    Prints both addresses. Neither should be empty.

    you@fedora:~
    echo "VSI public=$VSI_IP  private=$VSI_PRIV"

    Create the Transit Gateway and connect both sides

    3.17Builds: Transit Gateway

    A Transit Gateway is a router between IBM Cloud networks. With the default local routing it joins networks in one region, which is all you need because the VPC and dal10 are both in us-south.

    you@fedora:~
    ibmcloud tg gateway-create --name "$P-tg" --location us-south
    3.18

    Finds your gateway by name and saves its ID; every other tg command needs it.

    you@fedora:~
    export TG_ID=$(ibmcloud tg gateways --output json \
  | jq -r --arg n "$P-tg" '.. | objects | select(.name? == $n) | .id' | head -1)
    3.19Wait game

    Waits for the gateway to be available, usually within a minute.

    you@fedora:~
    python3 pvs-wait.py gateway
    3.20Builds: Gateway to VPC connection

    Plugs your VPC into the gateway. A connection is one network attached to a gateway; the gateway learns the network's address ranges from it.

    you@fedora:~
    ibmcloud tg connection-create "$TG_ID" --name "$P-vpc-conn" \
  --network-type vpc --network-id "$VPC_CRN"
    3.21Builds: Gateway to workspace connection

    Plugs your PowerVS workspace into the same gateway. Now the gateway has routes both ways: VPC 10.240.x.x to PowerVS 192.168.50.x and back. The VPC picks up the route automatically.

    you@fedora:~
    ibmcloud tg connection-create "$TG_ID" --name "$P-pvs-conn" \
  --network-type power_virtual_server --network-id "$WS_CRN"
    3.22Wait game

    Waits until both connections are attached, usually a few minutes.

    you@fedora:~
    python3 pvs-wait.py connections

    Save your variables

    3.23

    Adds this step's values to your file.

    you@fedora:~
    cat >> ~/pvs-lab.env <<EOF
export VPC_CRN="$VPC_CRN" SG_ID="$SG_ID" TG_ID="$TG_ID"
export VSI_IP="$VSI_IP" VSI_PRIV="$VSI_PRIV"
EOF
    ExpectA running VSI with a floating IP, and two gateway connections showing attached. In the diagram, the VPC side and the gateway are filled in.

    Wait for AIX and find its addresses

    4.1Wait game

    Waits for the server to be ACTIVE. If step 3 took a while it may already be ready and this returns at once. Otherwise, more Packet Snake.

    you@fedora:~

    Shows the server's details, including both networks: a public address on $P-pub and a 192.168.50.x address on $P-priv.

    you@fedora:~

    4.3

    Saves the public address, the one Cloud Shell can reach.

    you@fedora:~
    export AIX_IP=$(ibmcloud pi instance get "$AIX_ID" --json \
  | jq -r '[.networks[].externalIP // empty | select(. != "")][0]')
    4.4

    Saves the private address, the one the VPC will reach through the gateway.

    Path 1: Cloud Shell to AIX over the internet

    4.7Builds: SSH: Cloud Shell to AIX

    Logs in to AIX as root through its public address. PowerVS put your key on root, and your SSH config supplies the key. You should see the AIX welcome banner and a # prompt. The next commands run on AIX.

    you@fedora:~
    ssh root@"$AIX_IP"
    4.8

    The exact AIX level, starting with 7300.

    root@aix:/
    oslevel -s
    4.9

    Two addresses: the public one (first card, en0) and 192.168.50.x (second card, en1).

    root@aix:/
    ifconfig -a | grep inet
    4.10

    The routing table. The default route leaves through the public card. That is right for the internet, but it means replies to your VPC (10.240.x.x) would also go out the public card, where they cannot reach the VPC.

    root@aix:/
    netstat -rn
    4.11Builds: Route on AIX

    Fixes that: traffic for the VPC's whole 10.240.0.0/16 range now goes through the private subnet's gateway, 192.168.50.1, and from there through the Transit Gateway. This route lasts until AIX reboots, which is fine for a lab.

    root@aix:/
    route add -net 10.240.0.0 -netmask 255.255.0.0 192.168.50.1
    4.12

    Shows your new route.

    root@aix:/
    netstat -rn | grep 10.240
    4.13

    Logs out and returns you to Cloud Shell.

    root@aix:/
    exit
    4.14

    Saves the AIX addresses.

    you@fedora:~
    cat >> ~/pvs-lab.env <<EOF
export AIX_IP="$AIX_IP" AIX_PRIV="$AIX_PRIV"
EOF

    sshTransit Gateway

    Path 2: from the VPC across the Transit Gateway

    Now reach AIX the way an application in your VPC would: from the Ubuntu VSI, to AIX's private address, through the Transit Gateway. Nothing on this path touches the internet after Cloud Shell reaches the VSI.

    Check from the VSI

    5.1

    Runs one command, hostname, on the VSI and returns. IBM's Ubuntu images put your key on the ubuntu user and do not allow root logins, so you log in as ubuntu. Seeing $P-vsi proves your key, the floating IP, and the SSH rule all work.

    you@fedora:~
    ssh ubuntu@"$VSI_IP" hostname
    5.2

    Has the VSI ping AIX's private address. Cloud Shell fills in $AIX_PRIV before sending, so the VSI receives the real address. Three replies means traffic is crossing the Transit Gateway in both directions.

    you@fedora:~
    ssh ubuntu@"$VSI_IP" "ping -c 3 $AIX_PRIV"

    Log in to AIX through the VSI

    you@fedora:~/tz-lab-terraform-demo/lab/terraform
    ssh -i ~/.ssh/pvs-lab root@"$AIX_IP"
    5.8

    The AIX level.

    root@aix:/
    oslevel -s
    5.9

    The public address and a 192.168.100.x private one. The CLI track sees 192.168.50.x on its server; this one is 192.168.100.x.

    root@aix:/
    ifconfig -a | grep inet
    5.10

    Back to the lab machine.

    root@aix:/
    exit

    Path 2: from the VPC across the transit gateway

    5.11

    Saves the Ubuntu addresses Terraform created in the first apply. VSI_IP is the floating IP. VSI_PRIV is the address on the VPC subnet, the 10.240.x.x you will ping from AIX. IBM's Ubuntu images put your key on the ubuntu user and do not allow root logins.

    you@fedora:~/tz-lab-terraform-demo/lab/terraform
    export VSI_IP=$(terraform output -raw ubuntu_public_ip)
export VSI_PRIV=$(terraform output -raw ubuntu_private_ip)
echo "VSI public:  $VSI_IP"
echo "VSI private: $VSI_PRIV"
    5.12

    Runs hostname on the Ubuntu server and returns. Seeing the -tf-vsi name proves your key, the floating IP, and the SSH rule all work.

    you@fedora:~/tz-lab-terraform-demo/lab/terraform
    ssh -i ~/.ssh/pvs-lab ubuntu@"$VSI_IP" hostname
    5.13

    Has the Ubuntu server ping AIX's private address. The shell fills in $AIX_PRIV before sending, so the server receives the real address. Three replies means traffic is crossing the transit gateway in both directions.

    you@fedora:~/tz-lab-terraform-demo/lab/terraform
    ssh -i ~/.ssh/pvs-lab ubuntu@"$VSI_IP" "ping -c 3 $AIX_PRIV"

    Log in to AIX through the Ubuntu server

    5.14Builds: SSH: VSI to AIX

    The inner ssh logs in to the Ubuntu server as ubuntu and opens a tunnel (-W). The outer ssh uses that tunnel to log in to AIX's private address as root. -i has to be on both commands: with -J, that option is applied only to the final host, so the Ubuntu server never sees your key and answers Permission denied (publickey). Your key stays on the lab machine. The next commands run on AIX.

    you@fedora:~/tz-lab-terraform-demo/lab/terraform
    ssh -i ~/.ssh/pvs-lab \
  -o ProxyCommand="ssh -i ~/.ssh/pvs-lab -W %h:%p ubuntu@$VSI_IP" \
  root@"$AIX_PRIV"
    5.15

    Shows your login and, in brackets, where it came from: the Ubuntu server's 10.240.x.x address, not the lab machine. Proof you arrived through the VPC.

    root@aix:/ (via the VSI)
    who am i
    5.16

    Pings back the other way. Replace <vsi-private-address> with the VSI private address printed in step 5.11. Lab-machine variables do not exist on AIX.

    root@aix:/ (via the VSI)
    ping -c 3 <vsi-private-address>
    5.17

    Logs out of AIX and back to the lab machine.

    root@aix:/ (via the VSI)
    exit
    ExpectPing replies from the Ubuntu server, and who am i on AIX showing a 10.240.x.x address. The diagram is complete: two paths into one AIX server.
